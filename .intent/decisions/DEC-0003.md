## Context

Library code that throws errors forces callers to wrap everything in try/catch and makes the error surface invisible in function signatures. This is especially problematic for a library intended to be used by AI agents and CLI tools.

## Decision

All `core` functions return `Result<T, IntentError>` — a discriminated union of `Ok<T>` and `Err<IntentError>`. No thrown errors in library code. The CLI and MCP layers handle `Result` values and decide how to surface errors (exit codes, MCP error responses).

## Consequences

- Error paths are explicit in function signatures — callers cannot ignore them
- TypeScript narrows `result.value` only after checking `result.ok`
- `intentError(code, message, cause?)` is the single error constructor
- Error codes are a typed enum (`IntentErrorCode`) — consumers can switch on them
- CLI needs `process.exit(1); return;` after each error to satisfy narrowing
